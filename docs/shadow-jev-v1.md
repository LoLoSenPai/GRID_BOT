# Jev shadow V1

Shadow capture is controlled by `portfolios.shadow_jev_enabled` for each portfolio. The activation migration enables the existing live V2 portfolio containing active BTC and SOL bots; future portfolios default to disabled. Paper portfolios can also be enabled with `pnpm db:shadow-portfolio -- enable <portfolioId>` and disabled with the corresponding `disable` command. The portfolio manager builds the same policy observation as usual and schedules shadow persistence independently of its policy writes. A separate, one-connection database pool with short timeouts handles capture, so a slow or failed shadow snapshot/outbox write is logged without being awaited by the policy cycle. Capture stores an immutable market snapshot, the exact policy input and an outbox row in one transaction. Multiple bands can reference the same market snapshot. The engine does not read Jev results.

The Jev consumer is a separate process. Apply the database migration with `pnpm db:deploy`, set `TYPESAFE_API_KEY` only in the consumer environment, then run `pnpm --filter @grid-bot/worker shadow:start` or start the Compose `shadow` profile. If the consumer is stopped or Jev is unavailable, captured observations remain in the outbox for retry. Do not put the TypeSafe key in a client-side environment variable.

The V1 question set and requested Jev model are versioned in `apps/worker/src/shadow-jev-questions.ts`. It asks for recent regime (`range`, `drift_up`, `drift_down`, `unstable_transition`, `insufficient_evidence`), a temporary-outside-band Noul only when relevant, and whether the current band remains structurally suitable. The temporary excursion is defined as at least one of the next six hourly candles closing inside the original inclusive band. These are observations for later measurement, not trading instructions. The consumer sends only the latest 24 closed candles and band facts, then persists the full response, probability distribution, requested and resolved model versions, latency, request and errors. `Score` and policy-alternative replay are outside V1.

For comparison, join the observation, market snapshot, deterministic policy outcome and Jev outbox record by observation ID. The market snapshot preserves the exact closed-candle prefix used at decision time. A live portfolio with `autoLive=false` can be observed without applying or recording a portfolio-policy decision; its shadow outcome is `observed_only`. Future outcome labels must be computed separately at predeclared horizons; never add future candles to the Jev request. The TypeSafe API key is independent of the Codex MCP `evaluate` installation.

Status meanings: `pending` awaits processing; `processing` has a bounded lease; `failed` retains an error and may be scheduled for retry; `completed` retains the validated response. Each finished attempt is preserved in `shadow_jev_attempts`; an expired processing lease is logged as `LEASE_EXPIRED` and reclaimed after a consumer crash. After five unsuccessful calls, a job is terminal and remains available for audit. Observation capture and Jev processing have separate failure paths; shadow failures do not feed back into the portfolio policy.

The capture transaction is intentionally asynchronous relative to the policy cycle. A process crash before that transaction commits, or a database failure, can leave a gap in the shadow dataset; the bot continues and the failure is logged. Once capture commits, the persistent outbox survives Jev outages and consumer restarts.
